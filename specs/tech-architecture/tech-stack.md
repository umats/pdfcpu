# Project Context

Cold map of the repository as inspected on 2026-09-24. Paths below are evidence for observed behavior, not architectural requirements.

## Stack

- **Go library and CLI:** fork module `github.com/umats/pdfcpu` (upstream base `4d0e9ff2`), `go 1.26.0`; the CI matrix tests Go 1.26/1.27 on Linux, macOS, and Windows and cross-builds wasm, Linux ARM, and ARM64 (`go.mod`, `.github/workflows/test.yml`). No web server, database, ORM, authentication framework, or UI was found in the application entry points.
- **CLI:** Cobra v1.10.2 (`cmd/pdfcpu/root.go`). The public Go integration surface is `pkg/api`; `pkg/cli` is a programmatic command/dispatch layer, not an HTTP client (`pkg/api/api.go`, `pkg/cli/dispatch.go`).
- **Other direct dependencies:** `go.yaml.in/yaml/v3` for configuration, `github.com/google/jsonschema-go` for configuration-schema artifact tests, `github.com/hhrutter/tiff` and `golang.org/x/image` for images, `golang.org/x/crypto` for cryptographic protocols, `golang.org/x/text` for text normalization, and `github.com/mattn/go-runewidth` for terminal formatting (`go.mod`, `pkg/pdfcpu/model/parseConfig.go`, `pkg/pdfcpu/model/configuration_schema_artifact_test.go`, `pkg/pdfcpu/model/image.go`, `pkg/pdfcpu/crypto.go`). Versions are pinned in `go.mod`; no deprecation claim follows from the repository alone.
- **Data formats:** PDF is the primary input/output; configuration is YAML with a schema version; some operations emit or accept JSON (for example `cmd/pdfcpu/config.go`, `pkg/cli/document_exec.go`, `pkg/pdfcpu/create/`). These are file/CLI formats, not a REST or GraphQL API.

## Architecture

- **Entry points:** `cmd/pdfcpu/main.go` creates a signal-cancellable Go context and runs the Cobra root in `cmd/pdfcpu/root.go`. Library consumers call exported `pkg/api` functions directly. `pkg/samples/` contains examples; `internal/` contains private filesystem, network, context, font, and filter helpers.
- **Typical validation flow:** `cmd/pdfcpu/document.go` parses CLI flags and builds a `pkg/cli.Command` → `cmd/pdfcpu/common.go` calls `cli.Dispatch` → `pkg/cli/dispatch.go` selects a handler by `model.CommandMode` → `pkg/cli/document_exec.go` calls `api.ValidateFileWithReport` / `api.ValidateWithReport` → `pkg/api/validate.go` reads and validates → `pkg/pdfcpu/read.go` builds the PDF cross-reference model → `pkg/pdfcpu/validate/` checks PDF semantics. Mutations additionally use `pkg/pdfcpu` operations and `pkg/pdfcpu/write.go` to serialize results.
- **Dependency direction:** CLI presentation/argument handling in `cmd/pdfcpu`; typed command construction, dispatch, stdin/stdout handling, and output formatting in `pkg/cli`; reusable operation orchestration and file/stream boundaries in `pkg/api`; parsing, transformation, validation, cryptography, signatures, and PDF primitives in `pkg/pdfcpu` and its subpackages (`model`, `types`, `validate`, `sign`, `create`, `form`, etc.). This is layered by operation and PDF subsystem, not a controller/service/repository stack (`pkg/cli/dispatch.go`, `pkg/api/api.go`, `pkg/pdfcpu/model/context.go`).
- **I/O and state:** API operations generally expose both `io.ReadSeeker`/`io.Writer` and file-based variants; file entry points manage opening, closing, and staged writes (`pkg/api/api.go`, `pkg/api/validate.go`, `pkg/api/file.go`). `model.Context` owns a configuration, cross-reference table, and read/optimization/write state for one document (`pkg/pdfcpu/model/context.go`). `pkg/cli/dispatch.go` and `pkg/api/api.go` clone supplied configurations for individual operations.
- **Configuration:** `api.LoadConfiguration` supports auto, read-only, and stateless modes; discovery uses an explicit root, then `PDFCPU_CONFIG_ROOT`, then the OS config directory (`pkg/api/configuration.go`). The CLI `--conf disable` selects stateless mode; command initialization sets verbosity loggers (`cmd/pdfcpu/root.go`). The embedded defaults and schema-version handling live in `pkg/pdfcpu/model/configuration.go`; YAML parsing is in `pkg/pdfcpu/model/parseConfig.go`.

## Conventions (Observed)

- **Errors:** Go `error` returns, sentinel errors, `errors.Is`/`errors.As`, contextual `%w`, and `errors.Join` for multiple failures (`pkg/api/errors.go`, `pkg/api/validate.go`, `pkg/api/file.go`). `fault.Fail`/`fault.Catch` is a specialized panic-to-error mechanism for PDF conformance faults; dispatcher catches unexpected panics too (`pkg/pdfcpu/fault/fault.go`, `pkg/cli/dispatch.go`). CLI errors reach stderr and exit status 1 at `main`; there is no HTTP/global exception handler (`cmd/pdfcpu/main.go`).
- **API shapes:** Exported Go functions use explicit `context.Context` and typed configuration pointers, with a number of optional report/progress variants. Cobra flags use kebab-case; configuration YAML keys and tagged JSON output generally use camelCase (`pkg/api/validate.go`, `cmd/pdfcpu/document.go`, `pkg/pdfcpu/model/parseConfig.go`, `pkg/cli/document_exec.go`). The CLI emits both human-readable lines and optional JSON; there is no universal response envelope.
- **Types:** Statically typed Go. `model.CommandMode` and a typed `Command` connect dispatch to operation handlers; `model.Context` represents the PDF in memory (`pkg/cli/command.go`, `pkg/cli/dispatch.go`, `pkg/pdfcpu/model/context.go`). Small interfaces appear at specific seams, for example `log.Logger` and the revocation resolver/dialer (`pkg/log/log.go`, `pkg/pdfcpu/sign/revocation_http.go`); this is not a pervasive dependency-injection framework.
- **Observability:** `pkg/log/log.go` provides process-wide, opt-in category loggers backed by standard `log`, configured by CLI verbosity in `cmd/pdfcpu/root.go`; messages go to stderr by default. `pkg/api/progress.go` exposes per-operation progress callbacks. No long-running server, health endpoint, tracing, or structured JSON logging is present in the inspected runtime paths.
- **Tests:** Standard Go `_test.go` tests alongside packages plus black-box scenarios in `pkg/api/test`, `pkg/cli/test`, and `cmd/pdfcpu/test`; PDF/image fixtures under `pkg/testdata`, `pkg/filter/testdata`, and samples. Targeted error-path, platform-specific, network/HTTP-test-server, integration, and benchmark tests exist (`pkg/api/file_test.go`, `pkg/pdfcpu/sign/revocation_http_test.go`, `pkg/api/test/api_test.go`). CI runs `go vet`, `go test ./...`, and Linux coverage across packages (`.github/workflows/test.yml`); this map does not claim a measured coverage percentage.

## Signals / Active Considerations

- **Large shared core:** `pkg/pdfcpu/read.go` is over 4,000 lines; `stamp.go`, `crypto.go`, and `optimize.go` are also large. Reading, validation, and writing all meet at `model.Context`, so changes to that shared model have a broad blast radius (`pkg/pdfcpu/read.go`, `pkg/pdfcpu/model/context.go`, `pkg/pdfcpu/write.go`). Size is a navigation/review hotspot, not by itself evidence of a defect.
- **Global versus per-operation state:** configuration is cloned per dispatch/API operation, but loggers, CLI flag variables, and some font/config directories remain package globals (`pkg/cli/dispatch.go`, `pkg/api/api.go`, `pkg/log/log.go`, `cmd/pdfcpu/root.go`). Assess concurrent use and test isolation before changing these boundaries.
- **Network behavior is operation-specific:** signature revocation uses a URL-validated, IP-filtered HTTP client (`pkg/pdfcpu/sign/revocation_http.go`); optional `validate --links` uses a separate `http.Client.Get` path with timeout and offline check (`pkg/pdfcpu/validate/xReftable.go`). Do not assume these share the same network policy; review that path before processing untrusted PDFs with link checks enabled.
- **PDF conformance is evolving:** README explicitly limits PDF 2.0 validation to basic support. Strict/relaxed validation modes and validation notices preserve compatibility with encountered documents (`README.md`, `pkg/api/validate.go`, `pkg/cli/document_exec.go`). New features should consider both modes and round-trip fixtures.
- **Safe file mutation is centralized but has more than one boundary:** `pkg/api/file.go` stages output and commits/replaces after successful processing; core `pkg/pdfcpu/write.go` has a separate staged writer. For file-writing changes, trace both the API wrapper and core writer rather than assuming all paths share one transaction.
